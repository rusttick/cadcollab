## 2. Identity/versioning model

**Not a PDM identity scheme — this PR changes what "the file" contains,
specifically so that external version control (git or otherwise) can do
its job better.** No item numbers, no UUIDs, no revision fields are
touched anywhere in the diff. What it actually does:

- Adds a new document property, `DocumentCacheDir` (`PropertyPath`,
  `App::Document`, `Document.cpp`/`.h`), naming an external directory
  (absolute, or relative to the `.FCStd` file's own location —
  `resolveDocumentCacheDir`). When set, on save
  (`Writer::writeFilesToCacheDir`) any embedded "file" inside the FCStd
  zip that is marked `canBeCachedForDocument()` (a new flag on
  `Base::Persistence`, the base class every serializable FreeCAD object
  derives from) is written to that external directory **instead of**
  into the `.FCStd` zip itself; on load, the same files are read back
  from there (`XMLReader::readFilesFromCacheDir`).
- **This inverts where "derived/regenerable" content lives relative to
  "authored/source" content.** The two concrete things marked cacheable
  in this diff are (a) `Thumbnail` (`Gui/Thumbnail.cpp`, a rendered PNG
  preview — pure derived output, trivially regenerable, but has been
  causing spurious binary diffs in every commit forever) and (b)
  **BRep shape files** (`.brp`) for any feature object whose new
  `CanComputeShape` flag is true — wired up individually in
  `Part::FeaturePartBox` (unconditionally true), `Part::Feature` (set
  dynamically via a `signalStartSaveDocument` connection reading
  `CanComputeShape`), `PartDesign::Feature`/`FeatureAddSub`, and
  `Sketcher::SketchObject`'s `InternalShape`. A BRep file is the
  **tessellated/computed geometry cache** for a parametric feature — in
  principle always reproducible by recomputing the document from its
  parametric definition, but historically stored in the FCStd zip
  anyway (partly as a correctness safety net, partly because there was
  no other place to put it).
- **Identity of a cached file is filename-based, exactly like the
  problem this whole census keeps re-encountering**: `readFileFromCacheDir`
  matches on `entry.FileName` (the same name the object would have used
  inside the zip) under the configured cache directory — there is no
  separate stable ID; if two different documents happened to produce a
  colliding cache filename, the second would need per-document cache
  directories to stay distinct (which `DocumentCacheDir` being
  per-document, not global, ensures in practice — each document points
  at its own directory, so collision is a configuration risk, not an
  inherent design flaw).
- **Backward compatibility is handled by graceful absence, not a schema
  version bump**: if `DocumentCacheDir` is empty (the default), every new
  code path is a no-op (`writeFilesToCacheDir`/`readFilesFromCacheDir`
  both early-return) and behavior is bit-for-bit the historical FreeCAD
  behavior — files stay embedded in the zip exactly as before. This is a
  deliberately opt-in, additive feature, not a breaking format change —
  worth flagging as a real, working instance of the "small, low-cost
  code change... adopted independently... without requiring anyone to
  merge efforts" framing `technical_convergence_plan.md`'s own opening
  paragraph is explicitly looking for, except here the "adoption" is
  within FreeCAD core itself rather than across separate projects.

## 3. Conflict/concurrency strategy

**Not addressed by this PR, and not the problem it's solving.** This PR
does not touch locking, ownership, or multi-user editing in any way —
it's entirely about **single-document save/load content shaping**. Its
relevance to Cluster 2 is indirect but real: by moving noisy, derived
binary content (BRep caches, thumbnails) out of the versioned file and
into an external, presumably-`.gitignore`d cache directory, it directly
reduces the **volume and frequency of spurious binary diffs** that make
git-based (or any diff/merge-based) FreeCAD collaboration painful in the
first place — the same noise-control problem `HistoryWorkbench`
addresses at the *diff-presentation* layer (excluding properties/types
from its own comparison view) this PR addresses at the *storage* layer
(don't put the noisy content in the versioned file at all). These are
complementary, not competing, approaches to the same underlying
friction point, and the `Versioning.py::test_diff` test is explicit
proof-of-concept that the technique works: with `DocumentCacheDir` set,
a `Document.xml` diff between two saves after changing one dimension
shrinks to exactly two lines (the filename and the changed float value)
— see the literal `expected_diff` assertion in the new test.

## 4. File format / serialization touchpoints

This section is where nearly all of this PR's substance lives:

- **`App::ProjectFile`** (the `.FCStd` zip reader/metadata layer) gains
  `containsFileInDocumentCache`/`readInputFileFromDocumentCache`,
  checked as a fallback wherever code used to assume "if it's not in the
  zip, it doesn't exist" — e.g. `Mod/Start/App/FcstdInfoSource.cpp`'s
  thumbnail loader for the FreeCAD Start page now checks both the zip
  and the cache dir before giving up. This is the right integration
  point for any future project wanting to build tooling (like the Start
  page, or `HistoryWorkbench`-style browsers) that reads FCStd metadata
  without a full FreeCAD session — the cache-dir fallback has to be
  replicated by any such external reader too, which is worth flagging as
  a portability cost of this design (see §8).
- **`Base::Writer`/`Base::XMLReader`** (the generic persistence I/O layer
  used by every `Persistence`-derived object, not just shapes) gain the
  actual cache read/write methods (`writeFilesToCacheDir`,
  `readFilesFromCacheDir`) and a `documentCacheDir` field threaded
  through from `Document::saveToFile`/`restore`. `FileWriter::putNextEntry`
  is changed to `fs::create_directories(path.parent_path())` before
  opening the output stream — a small, necessary robustness fix given
  the cache dir may have arbitrary nested structure never needed when
  everything just went into a flat zip.
- **`Base::Persistence::canBeCachedForDocument()`/`setCanBeCachedForDocument()`**
  is the single new extension point every object type opts into — a
  plain boolean flag, default `false` (so nothing changes for any object
  type that doesn't explicitly opt in). This is a clean, minimal-surface
  design: adding cache-dir support for a new feature type elsewhere in
  FreeCAD (or in a third-party workbench) requires exactly one flag flip
  plus (for a dynamically-cacheable case like `Part::Feature`) one
  `signalStartSaveDocument` connection — a template any workbench author
  could copy directly.
- **`App::Document::addRecomputeObject`** gains a `forMigration` parameter
  (default `true`, preserving old callers' behavior unchanged) —
  distinguishing "this object needs recompute because we're migrating an
  old file format" from "this object needs recompute because its cached
  shape is simply missing" (`Feature::onDocumentRestored`, `PartFeature.cpp`
  line ~1657: if `CanComputeShape` is true but `Shape` is null after
  restore — i.e. the BRep cache file wasn't found, most likely because
  the document was opened on a machine without access to the
  `DocumentCacheDir` — mark it touched for recompute rather than
  silently leaving a blank shape). `Versioning.py::test_mark_to_recompute`
  is the direct test of exactly this scenario (manually deleting a cached
  `.brp` file, then reopening, then asserting `"Touched" in doc.Box.State`).
  This is the mechanism that makes the whole feature safe to ship: if the
  cache is unavailable or stale, FreeCAD degrades to "recompute it," not
  "silently show wrong/missing geometry."
- **A parallel, unrelated-but-bundled cleanup**: `App::ProjectFile.cpp`'s
  Xerces XML property-name matching is refactored from hand-built
  `std::array<XMLCh,N>` literal-character arrays
  (`chLatin_P, chLatin_r, ...`) to a new `XMLTools::toXMLCh<N>()`
  `constexpr` helper (`Base/XMLTools.h`) — a pure readability/maintenance
  improvement riding along in the same PR, plus a genuine new capability
  (recognizing `Uuid`/`Path`-typed metadata properties, needed because
  `DocumentCacheDir` itself is stored as a `Path`-typed property in the
  FCStd metadata, not a plain `String` like the other document metadata
  fields).

## 5. Dependencies & integration points

- **No new external dependency** — uses `std::filesystem` (already a
  project dependency at the C++17+ level this codebase is clearly on)
  for path resolution/directory creation, and the existing `zipios`
  library for the zip side, unchanged.
- **Cross-module integration cost is real and visible in the diff
  itself**: enabling BRep caching required near-identical
  `signalStartSaveDocument`-connection boilerplate independently added
  to `Part::Feature`, `PartDesign::Feature`, `PartDesign::FeatureAddSub`,
  and `Sketcher::SketchObject` — four copies of essentially the same
  five-line lambda. This is a small but concrete "this pattern should
  probably be a helper, not copy-pasted four times" observation — not a
  blocking issue, but a legitimate simplification opportunity a reviewer
  would likely flag, and relevant to field 8 (see below) since it's
  exactly the kind of "small shim, adopted independently by several
  places" cost the technical-convergence plan is trying to find and
  minimize.
- **`fcinfo`** (a standalone Python maintainer script, `src/Tools/fcinfo`,
  used to inspect/diff FCStd internals from the command line — its own
  docstring includes a "Git usage" section) gets a `-nd`/`--nodoc` flag
  to suppress printing the document's own path and SHA1 hash — a minor,
  clearly-related addition (useful when comparing two differently-named
  cache-dir test outputs, exactly as `Versioning.py`'s own diffing logic
  does) rather than scope creep.

## 7. Friction points observed firsthand

- This PR is a **first-party, core-level answer to exactly the friction
  point `doc/optimistic_locking_research.md`'s literature survey frames
  as fundamental** ("CAD conflicts are geometric/topological
  incompatibilities, not line diffs" — §1 of that survey) — except this
  PR doesn't attempt to solve *diffing* or *merging* shape data at all;
  it sidesteps the problem by **not versioning the shape data in the
  first place** when it's reproducible from the parametric definition.
  This is architecturally the same insight `ose-vcs-library` embodies
  independently (don't version the compiled artifact, version the
  source that produces it) — but arrived at from the opposite direction:
  `ose-vcs-library` never had binary artifacts in git to begin with;
  this PR retrofits that same principle onto FreeCAD's existing
  binary-embedding format, for the subset of content (BRep caches,
  thumbnails) that's genuinely just a cache of already-versioned
  parametric data.
- **The `test_diff` test result is the single most concrete, measurable
  piece of evidence anywhere in this census for what "git-friendly CAD
  file format" actually looks like in practice**: a two-line diff for a
  one-dimension change, instead of an opaque full-binary diff. This is
  worth treating as a benchmark/target, not just a nice property — any
  future proposal aiming at Cluster 2's friction point could point to
  this exact test as "the bar to clear."
- **The four-times-repeated `signalStartSaveDocument` wiring (§5)** is a
  small, real instance of the plan's own target problem *within a single
  codebase*: even inside FreeCAD core, "make an existing feature type
  participate in the new caching mechanism" isn't yet a one-line opt-in
  — it's a signal-connection idiom that has to be hand-copied per
  feature class. If this PR (or a follow-up) doesn't consolidate that
  into a shared base-class default or mixin, third-party workbenches
  wanting the same benefit for their own custom feature types would face
  the identical copy-paste tax, which is exactly the kind of thing a
  "small, low-cost, independently-adoptable" convention (this plan's own
  framing) should try to avoid perpetuating.

## 8. Minimal-patch hypothesis

- **This PR itself already *is* the kind of minimal patch the plan's
  opening paragraph describes** — small, additive, opt-in, no format
  version bump, no requirement that anyone merge codebases. If merged
  into FreeCAD core, every project in this census that already invokes
  real FreeCAD (`HistoryWorkbench`, `ose-vcs-library`'s `freecadcmd`
  dependency, EasyPDM's/the Omniverse connector's FreeCAD macros) would
  gain the option to reduce FCStd diff noise for free, with zero code
  changes of their own beyond setting `doc.DocumentCacheDir` and
  `.gitignore`-ing that directory. This is a stronger, more central
  version of exactly the "tiny shared fix" the plan is looking for —
  except the fix belongs in FreeCAD core rather than in any downstream
  project, which changes the adoption story: **the actionable patch
  proposal here isn't "each project adds this," it's "each project that
  cares about this friction point should track/support merging PR
  #28312,"** a fundamentally different (advocacy/prioritization) kind of
  recommendation than the code-shim proposals in the other architecture
  notes.
- **A smaller, more code-shim-shaped follow-on** worth naming
  separately: consolidating the repeated `signalStartSaveDocument`
  wiring (§5, §7) into a shared, reusable pattern (e.g. a
  `CacheableShapeFeature` mixin/base behavior) — cost: **trivial**, pure
  internal refactor, but it directly lowers the adoption cost for any
  third-party feature type (in FreeCAD core or an external workbench)
  wanting the same caching benefit, which matters more the more this
  pattern is expected to spread.
- **Downstream implication for every project in this census that
  already manipulates FCStd files directly** (EasyPDM's attachment
  storage, the Omniverse connector's STEP export pipeline,
  `HistoryWorkbench`'s snapshot extraction): if this PR merges, any of
  them reading FCStd zips directly (rather than through FreeCAD's own
  API) would need to learn about the `DocumentCacheDir` fallback the
  same way `FcstdInfoSource.cpp` had to (§4) — i.e. **this PR quietly
  changes what "a complete FCStd file" means** for any external tool
  that assumes the zip is self-contained. Worth flagging explicitly as a
  compatibility consideration for the plan's eventual synthesis, not a
  reason to avoid the patch, but a real integration cost some other
  project in this census might have to pay if this lands.
