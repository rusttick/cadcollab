## 1. Repo & basic facts

- **Language(s)**: Python (Flask + SQLAlchemy, ~4,600 lines across
  `openpartslibrary/*.py`, largest files `routes.py` (1,025 lines) and
  `admin.py` (994 lines)); vanilla Bootstrap 5 + Bootstrap Icons for the
  UI (vendored under `static/`, not npm-managed) — no separate frontend
  build step, no JS framework.
- **Size/shape**: a single, small monolithic Flask app — one package
  (`openpartslibrary/`), one SQLite database file, no microservices, no
  separate worker process. Notably smaller and structurally simpler than
  Ondsel-Server, and simpler even than EasyPDM (no separate frontend
  build, no migrations directory — `db.py` just calls
  `Base.metadata.create_all()` on startup).
- **Deployment modes, plural, by design**: Flask dev server (`python
  app.py`), Docker Compose, **and a packaged Windows desktop app**
  (`run_desktop.py`, `desktop.py`, `scripts/build_windows_desktop.ps1`,
  producing a ZIP) — the desktop mode is a first-class target, not an
  afterthought, distinguishing this from every server-shaped project in
  the cluster so far.
- **License**: **AGPL-3.0** (`LICENSE` — full GNU AGPLv3 text) —
  `doc/ecosystem/graph.yaml` currently records `license: unknown`; this
  is a straightforward correction (see §6).
- **CI**: two workflows — `devsecops.yml` (name suggests a security/SCA
  scanning pipeline, not independently inspected in this pass) and
  `mirror-to-opencode.yml` (mirrors the repo to another platform —
  `opencode`, not independently verified what that refers to).
- **`publiccode.yml` present** — a structured metadata file used by
  public-sector open-source catalogs (Italy's/EU's
  publiccode.yml standard) — signals the author is deliberately
  targeting discoverability in public/government open-source registries,
  a distribution channel none of the other three projects in this
  cluster use.

## 2. Identity/versioning model

**No versioning at all — this is a reference catalog, not an editable
PDM record store.** This is the sharpest architectural contrast in the
cluster so far, more so even than Ondsel-Server's weak concurrency model
(which at least *has* a version list):

- `Component` (`models.py`) has exactly **one** `cad_file_id` — a
  single, current CAD file per component, no history, no version array,
  no revision-letter convention. A `revision` column exists
  (`String(10)`) but is a **free-text field imported verbatim from a
  spreadsheet** (`db.py`'s `import_from_spreadsheet`, `search.py`'s
  indexed/weighted search fields) — it is metadata *about* the part
  (e.g. "the manufacturer calls this Rev C"), not a system-enforced
  version chain the way EasyPDM's `revision_number` or Ondsel-Server's
  `fileVersionSchema` array are.
- Likewise `lifecycle_state` (`String(50)`, free text) has no enum
  constraint, no state-machine transitions, and no code anywhere in the
  files read that validates or acts on its value — contrast EasyPDM's
  enforced `w_pracy → sprawdzany → wydany → anulowana` state machine.
  This looks like a field carried through from a PLM-style spreadsheet
  import (i.e., informative for search/filtering) rather than an
  operational status this application itself manages.
- **Identity is a UUID per row** (`Component.uuid`, `File.uuid`,
  `Supplier.uuid`, `Material.uuid` — all `String(32)`/`String(8)`,
  generated by the importer, `db.py`) plus a separate human-facing
  `number` (`String(50)`) — structurally similar to EasyPDM's
  UUID+item_number pair, but **`number` here is not sequence-generated**;
  it's imported directly from the source spreadsheet
  (`row.get("number")`, inferred from `import_from_spreadsheet`'s
  column-mapping pattern), so uniqueness/collision handling is the
  importer's responsibility, not a database sequence — a materially
  weaker guarantee than EasyPDM's `item_number_seq`.
- **The "one-click BOM package" (`parts_package.py`) is itself a
  distribution/versioning mechanism of a different kind**: it exports
  or imports a **zip of a spreadsheet plus a CAD directory**
  (`PartsPackage.import_zip`/implied `export_zip`), with import
  explicitly **skipping components whose UUID already exists**
  (`skipped_existing_uuid_count` in `PartsPackageImportResult`) — i.e.
  the "sync" primitive between two OpenPartsLibrary instances (or a
  spreadsheet-based external catalog) is a whole-package,
  idempotent-on-UUID import, not a per-component update/merge. This is a
  bulk, catalog-level operation, not a per-part editing workflow.

## 3. Conflict/concurrency strategy

**None — and unlike Ondsel-Server, there is no evidence this gap is even
felt as a gap, because the tool isn't built for multiple people to edit
the same record concurrently.** No `owner`/`lock` fields anywhere in
`models.py` (the `owner` column on `Component` is a free-text string —
"who owns this part," organizationally, not a check-out lock), no
session/user model found (`grep` for login/User/password/session across
`openpartslibrary/*.py` turned up only incidental hits in `i18n.py`
and `session_boms.py` — the latter is a **per-browser-session shopping
cart** for "My Bill of Materials," not a multi-user account system).

This confirms the read from §1/§2: OpenPartsLibrary is architecturally a
**single-writer reference database with a spreadsheet-import pipeline**,
consumed by potentially many read-only users doing search/BOM-building,
not a multi-editor collaborative PDM tool. The "conflict" this project
actually needs to handle is **import collisions** (two imports
introducing the same UUID or `number`), which it handles simply — by
skipping already-known UUIDs — rather than anything resembling the
"lock, don't merge" pattern the EasyPDM/Anchorpoint/Omniverse-connector
cluster reinvents.

## 4. File format / serialization touchpoints

- **CAD files are opaque attachments** — `File`/`Component.cad_file`
  store a filesystem path/metadata record; there's no evidence in
  `models.py` or `downloads.py` of the application parsing or
  understanding CAD geometry itself (no FreeCAD Python import found
  anywhere in the files read) — contrast every other project in this
  census, all of which invoke FreeCAD or another CAD kernel directly.
  `openpartslibrary/tools/export_fcstd_to_3mf.py` and
  `render_3mf_thumbnail.py` exist as **standalone offline tooling**
  (used to prepare the bundled sample CAD library, almost certainly, not
  invoked live by the running Flask app based on their location under
  `tools/` rather than the main package) — worth a follow-up read if
  precise thumbnail-generation behavior ever matters for a patch
  proposal.
- **Spreadsheet is the canonical exchange format for bulk data** —
  `.ods`/`.xlsx` via `pandas` (`import_from_spreadsheet`,
  `PartsPackage.SPREADSHEET_NAMES`), not a database dump or an API
  payload. This is a deliberately low-tech, engineer-editable interchange
  choice — anyone can hand-edit a spreadsheet of parts without touching
  the application at all.
- **The standout finding of this whole repo**: `hbom.py` builds a real
  **SPDX 3.0.1 JSON-LD hardware bill of materials**
  (`build_spdx_hardware_bom`) — SPDX's `Package`/`Relationship`/`Bom`
  vocabulary, `contains` relationship edges, proper `spdxId`/
  `creationInfo` structure. This is a **standards-based export format**,
  unlike every other BOM/export mechanism read in this census so far
  (EasyPDM: bespoke CSV; Ondsel-Server: no BOM export mechanism read;
  the Omniverse connector: not applicable). SPDX is normally associated
  with *software* supply-chain/SBOM tooling — its extension to "hardware
  BOM" here is a genuine, portable idea: an interchange format any
  project in this census could emit *without adopting anything else*
  about this project's architecture, since it's a pure export-side
  transformation over whatever BOM structure a given tool already has
  internally.

## 5. Dependencies & integration points

- **Backend**: Flask + SQLAlchemy (declarative ORM) + SQLite (`db.py`) —
  no separate database server process, matching the desktop-app
  deployment target. `pandas` for spreadsheet I/O.
- **No auth, no external services, no message queue, no CAD kernel
  dependency in the main app** — by far the smallest external-dependency
  footprint of any project in this census except `ose-vcs-library`
  (which has none at all for its Tier 1 checks). `requirements.txt` was
  not enumerated line-by-line in this pass but the import list above
  (Flask, SQLAlchemy, pandas, presumably `openpyxl`/`odfpy` for
  spreadsheet formats) suggests a short, standard list.
- **Desktop packaging** is a real, maintained integration point
  (`run_desktop.py`, PowerShell build script) — worth noting as a
  distribution channel none of the server-first projects in this
  cluster offer.
- **`publiccode.yml`** integrates with public-sector open-source
  discovery catalogs — a distribution/governance touchpoint, not a
  runtime dependency.

## 7. Friction points observed firsthand

- This project doesn't participate in Cluster 2's "concurrency strategy"
  friction point at all — it has no concurrent-editing story to
  contribute, confirming (independently of `ose-vcs-library`) that not
  every project in this census actually needs the "lock, don't merge"
  pattern. Two clean counter-examples now on record for two entirely
  different reasons: `ose-vcs-library` (plain-text source makes locking
  unnecessary) and this project (single-writer catalog model makes it
  inapplicable).
- The real friction point this project *does* illustrate, matching
  Cluster 1's framing (shared standard-parts libraries) more than
  Cluster 2's: **CAD file exchange for standard/purchased parts is
  solved here by not solving CAD interoperability at all** — files are
  opaque blobs, matched to metadata by convention (filename, `File`
  row), with real geometry understanding pushed to offline tooling
  (`tools/export_fcstd_to_3mf.py`) rather than the running application.
  This is a pragmatic, low-cost answer to a problem (multi-format CAD
  compatibility) that other approaches in this census either avoid
  (`ose-vcs-library`'s parametric-source-of-truth) or partially solve at
  real integration cost (the Omniverse connector's STEP/USD pipeline).
- The SPDX hardware-BOM export (§4) is the most exportable, standards-
  aligned idea found in this census so far — every other project's BOM
  mechanism is bespoke.

## 8. Minimal-patch hypothesis

- **Not a candidate for the concurrency-control shim** (§3, §7) — same
  conclusion as `ose-vcs-library`, for different structural reasons.
- **The SPDX hardware-BOM export function is the strongest, most
  directly reusable artifact found in this entire census pass** — it is
  a **~90-line, dependency-free, pure-function transform**
  (`build_spdx_hardware_bom(components)` takes a list of plain dicts,
  returns a plain dict) with no coupling to this project's database,
  Flask app, or SQLAlchemy models. Cost to adopt elsewhere: **trivial**
  — literally copy the function (MIT/AGPL license terms permitting; this
  repo is AGPL-3.0, so a literal copy into another project carries
  copyleft obligations unless reimplemented independently from the SPDX
  3.0 spec, which is itself an open standard with no such encumbrance).
  This is a much stronger field-8 candidate than anything found in
  EasyPDM or the Omniverse connector: a genuinely small, portable,
  immediately-adoptable piece of interoperability code, not just a
  convention proposal.
- **A shared "BOM export interchange" convention** (moderate ambition,
  small cost per adopter): propose SPDX 3.0's hardware-BOM profile (or a
  close variant) as the common export target for every project in this
  census with any BOM concept at all (EasyPDM's CSV export, this
  project's own package-zip, any future Ondsel-Server BOM feature) —
  since it's export-only and additive, no project has to change its
  internal BOM representation, only add one more output format. This is
  arguably the single most actionable, low-risk cross-project patch
  surfaced in this technical-convergence phase so far, and worth
  flagging prominently when the plan's proposals get synthesized.
