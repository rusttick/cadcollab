This PR introduces a brand-new FreeCAD core module, **`Collaboration`**,
whose one shipped feature is a native, in-document **`Topic`**
annotation object — a labeled marker that can be pinned either to a
fixed point in space or directly to a piece of geometry. The
vocabulary (`Topic`) and the underlying idea (a discussion/issue marker
attached to a model element) are the same core concept
`BCF-Plugin-FreeCAD` implements as an *external interchange format*
(see that project's own architecture note) — this PR is the first
sign of that same concept becoming a **native FreeCAD document object**
rather than only an import/export format.

## 1. Repo & basic facts

- **Target**: `FreeCAD/FreeCAD` core, new module `src/Mod/Collaboration/`
  (App + Gui subdirectories, following the same App/Gui split every
  other FreeCAD module uses) plus a small, generically useful addition
  to `src/Gui/Utilities.{cpp,h}` (a reusable `DoubleClick` helper class,
  see §4) and one behavioral change to the existing
  `ViewProviderAnnotation.cpp`/`.h` (adding double-click detection to
  annotation-label dragging, which `Topic` builds directly on top of).
- **A real, complete, buildable module skeleton**: proper `CMakeLists.txt`
  files at every level, a new `BUILD_COLLABORATION` CMake option
  (default `ON`), `.pre-commit-config.yaml` updated to lint the new
  directory, and both an `App` (data model) and `Gui` (view provider +
  command + task dialog) half — this is a genuine, mergeable-shaped
  addition, not a proof-of-concept patch.
- **License**: LGPL-2.1-or-later, matching FreeCAD core generally and
  `doc/ecosystem/graph.yaml`'s recorded "LGPL-2.1 (FreeCAD core)" for
  this node — confirmed, no correction needed.
- **Explicit Ondsel attribution**: two files
  (`Gui/AppCollaborationGui.cpp`, `Gui/AppCollaborationGuiPy.cpp`)
  credit "Ondsel" directly in their copyright header, alongside Pieter
  Hijma's name — a concrete, source-level confirmation that this work
  is part of Ondsel's continuing FreeCAD-core involvement post-shutdown
  (the same "Ondsel Onward Fund"/NLnet-grant context already documented
  in `doc/architecture/ondsel-lens-addon.md`'s §1), not an unrelated
  third-party contribution that merely shares an author.
- **Very early / minimal-viable stage**: the one shipped UI capability
  is a task-panel dialog with exactly two editable fields (`Label`,
  `LabelText`/"Title" — see §4); there's no comment thread, no author/
  timestamp tracking, no BCF import/export, and no status/resolution
  concept anywhere in the diff. This is a foundational data-model PR,
  not a feature-complete collaboration tool.

## 2. Identity/versioning model

**Not really applicable in the sense the rest of this census uses the
term — this PR adds a new kind of *document object*, not a file-
identity or version-history mechanism.** Still, worth describing
precisely, since "how is a Topic identified and where does it live"
is the closest analogous question:

- A `Topic` (`Collaboration::Topic`, `App/Topic.cpp`) is a regular
  FreeCAD document object, subclassing `App::AnnotationLabel` (FreeCAD's
  existing floating-text-label mechanism) and mixing in
  `App::GroupExtension` — i.e. it inherits FreeCAD's own ordinary
  object-naming/identity machinery (an internal name plus a `Label`)
  rather than introducing any new ID scheme. Consistent with the
  pattern already flagged favorably in `taack-plm-freecad`'s
  architecture note (§2, §7 there): reach for FreeCAD's own existing
  identity primitives before inventing a new one.
- **Topics are auto-organized into a document-level group**: the new
  `Collaboration_Topic` command (`Gui/Command.cpp`) looks for (or
  creates) a document object group literally named `"Topics"`
  (`getTopicGroup()`) and adds every new `Topic` into it — a simple,
  effective convention keeping all of a document's discussion markers
  visually and structurally grouped in the tree view, with no
  configuration needed.
- **Placement has two modes**, controlled by a `PlacementType` enum
  property (`"Absolute"` | `"Geometry"`): a Topic can float at a fixed
  point (`BasePosition`, inherited from `AnnotationLabel`) or be
  anchored to a specific piece of geometry via a `PropertyLinkSub`
  named `Geometry` (a sub-element reference — face, edge, vertex —
  exactly the granularity BCF's own `Viewpoint`/`Component` selection
  model needs). `getGeometryPosition()` computes the actual anchor
  point using FreeCAD's existing `Attacher` engine (the same mechanism
  Sketcher/PartDesign use for datum attachment), trying an "Inertial
  CS" attach mode first and falling back to "Object XY" if that throws
  — a pragmatic, defensive two-tier fallback for a real range of
  geometry types.
- **No versioning of a Topic's own content** (no history of label/title
  edits, no comment thread) — this PR's `Topic` is a single, live,
  directly-editable object, closer in spirit to a sticky note than to
  BCF's `Comment`-per-`Topic` timeline model.

## 3. Conflict/concurrency strategy

**Not addressed, and not the point of this PR** — same conclusion as
PR #28312's note (§3 there): this is a single-document, single-user
feature addition with no multi-user awareness of any kind. Worth
noting for completeness only: because a `Topic` is an ordinary document
object stored inside the `.FCStd` file itself (not an external sidecar
or database record), it inherits whatever concurrency story the
*document* already has — i.e. none beyond what git or a PDM layer
wrapping the whole file provides, the same as any other FreeCAD
feature object. This is architecturally the opposite choice from BCF's
own model (an external, separately-versioned interchange file) and
worth flagging as a real design tension for any future work connecting
the two: an in-document Topic is easy to see and edit inline, but
"who changed this Topic and when" would need exactly the same kind of
audit-trail machinery this census has found in CADBase's
`component_history_list` or BCF's own `CreationAuthor`/`ModifiedAuthor`
fields — none of which this PR's `Topic` object has yet.

## 4. File format / serialization touchpoints

- **A genuinely reusable, generic addition rides along with this
  feature**: `Gui::DoubleClick` (`src/Gui/Utilities.{cpp,h}`) is a
  small, self-contained helper for detecting a double-click from raw
  Coin3D mouse events (comparing click time against
  `QApplication::doubleClickInterval()` and click position against a
  fixed pixel radius) — added here specifically so a `Topic`'s label
  can be double-clicked in the 3D view to open its edit dialog
  (`ViewProviderAnnotation.cpp`'s `dragStartCallback` now checks
  `doubleClickData.isDoubleClick(mbe)` and, if so, cancels the drag and
  calls a new virtual `labelDoubleClicked()` hook). This is a clean,
  minimal, independently useful utility class that any other FreeCAD
  view provider needing double-click detection could now reuse —
  small, but a real, generically beneficial side effect of this
  feature PR, unrelated to collaboration/versioning specifically.
- **The task dialog is intentionally minimal**: `task_topic_dialog.py`
  /`task_topic_dialog.ui` expose exactly two fields — `Label`
  (FreeCAD's own internal label property) and the first element of
  `LabelText` (referred to as "Title" in the dialog) — both plain
  two-way-bound `QLineEdit`s with no validation, no rich text, no
  attachments, no comment field. `logger.debug("Opening Task Topic
  Dialog")` and an `open()` method that does nothing else confirm this
  is scaffolding for a dialog that will clearly grow, not a finished
  feature surface.
- **No BCF read/write of any kind appears anywhere in this diff** — the
  shared vocabulary (`Topic`) is either a deliberate nod toward future
  BCF interoperability or simply the natural English word for "a
  labeled discussion point," and this pass found no direct evidence
  either way (no comment, commit message, or code referencing BCF, the
  standalone `BCF-Plugin-FreeCAD` addon, or the buildingSMART standard
  anywhere in the diff). Flagged explicitly as an open question rather
  than assumed — see §6/§7.

## 5. Dependencies & integration points

- **No new external dependencies** — built entirely on existing FreeCAD
  internals: `App::AnnotationLabel`/`App::GroupExtension` (data layer),
  `Gui::ViewProviderAnnotationLabel`/`Gui::ViewProviderGroupExtension`
  (view layer), the existing `Attacher` geometry-attachment engine, and
  Coin3D/Inventor event types already used throughout `Gui::Utilities`.
- **Menu/toolbar integration follows FreeCAD's newer "workbench
  manipulator" extension pattern**: `InitGui.py` registers a
  `CollaborationWorkbenchManipulator` that inserts the new
  `Collaboration_Topic` command right after the existing
  `Std_AnnotationLabel` command in the menu, and appends it to the
  "Tools" toolbar — i.e. this feature doesn't introduce its own
  workbench at all, it **extends whichever workbench is already
  active** by hooking into the shared "Tools" menu/toolbar, a lighter-
  weight integration style than a dedicated workbench tab.
- **A structural placement decision worth flagging for the plan's own
  taxonomy purposes**: this lives at `src/Mod/Collaboration/` as a
  first-class FreeCAD module (like `Part`, `Sketcher`, `PartDesign`),
  not inside an existing module — FreeCAD core's own naming already
  independently arrived at the word "Collaboration" for this feature
  area, which is worth keeping in mind if this census's own category
  taxonomy (`pdm`/`plm`/`bom`/`cloud-sharing`/`real-time-collab`/etc.)
  is ever revised — FreeCAD itself doesn't use any of those words for
  this concept.

## 7. Friction points observed firsthand

- **This is the first sign in this census of "design review /
  discussion annotation" moving from external-interchange-format
  territory (BCF) into native FreeCAD core document-object territory.**
  If this module grows to include comments, authorship, timestamps, and
  eventually BCF import/export, it would directly compete with or
  absorb the standalone `BCF-Plugin-FreeCAD` addon's purpose — worth
  flagging as a space to watch, not a conclusion to draw yet, since
  this PR's current scope (a label and a title field, no thread, no
  BCF I/O) is far short of that.
- **The reusable `DoubleClick` utility (§4)** is a small, generically
  useful piece of infrastructure that happened to ride along with this
  feature PR — worth noting for completeness as exactly the kind of
  small, independently-adoptable code unit this whole technical-
  convergence plan is looking for, even though it has nothing to do
  with PDM/versioning specifically.
- **The "extend the active workbench's Tools menu rather than ship a
  dedicated workbench" integration pattern (§5)** is a lighter-weight
  UI-integration style worth citing as an alternative to the
  dedicated-workbench pattern every third-party addon in this census
  uses (necessarily, since third-party addons can't modify another
  workbench's menu) — available to this PR only because it's shipping
  inside FreeCAD core itself, but worth remembering as the more
  "native-feeling" integration style core features can achieve that
  addons generally cannot.

## 8. Minimal-patch hypothesis

- **Too early-stage to evaluate as a "minimal patch" in the sense the
  rest of this plan uses the term** — this PR doesn't solve a
  friction point directly, it lays foundational data-model groundwork
  (a geometry-anchored annotation object) that a future PR could build
  a real collaboration/review feature on top of. The plan's own
  question ("is there a tiny shared fix") doesn't quite apply to a
  first-stage core feature addition the way it applies to a completed
  third-party tool.
- **The clearest actionable recommendation this note can make**: if
  this module is intended to eventually interoperate with or supersede
  BCF-style external exchange (an open question per §6, not confirmed),
  the cheapest way to find out is to ask directly in the PR's own
  GitHub discussion whether `BCF-Plugin-FreeCAD`'s author or maintainer
  has been consulted — before any further core investment duplicates
  work that project's `rdwr/` package (topic/comment/viewpoint
  read-write, XSD validation, incremental-write architecture — see that
  project's own architecture note, §2/§4) has already solved for the
  *interchange* half of this same problem space.
- **The `DoubleClick` utility (§4, §7)** is the one piece of this diff
  that's already a complete, adoptable, zero-cost artifact independent
  of everything else in the PR — nothing to propose here beyond noting
  it exists for anyone else touching Coin3D mouse-event handling in
  FreeCAD core.
